# WebShell 后门通信规则 · 质量、检出率、误报率与盲区分析

## 0. 结论

原 `04-WebShell后门通信.rules` 只有 2 条规则，覆盖面非常窄，且其中一条存在明确的方向性错误：

- 9104001 只按“文件名”匹配，误报高、变体漏报多；
- 9104002 的 PCRE 实际匹配的是参数**值**，而不是 `cmd=`/`exec=` 这类参数**名**；
  对最常见的 `shell.php?cmd=id` 反而**不命中**；
- 两条规则都只看 URI，不看 POST Body、Cookie、请求头；
- 没有响应侧确认，无法区分“访问了同名文件”和“WebShell 命令执行成功”；
- 没有正/反例 PCAP、没有 `suricata -T`、没有 CI。

当前场景已完成规则/Lua 重构，并通过 GitHub Actions：
run `42384924560`（commit `d621e7f`），17/17 PCAP 用例通过。
规则数量从 2 条扩展到 4 条，方向改为外部 -> 内部。
下面的“检出率/误报率”仍是机制分析，不是生产实测百分比。

## 1. 规则逐条审计

### 1.1 9104001 · 已知后门文件名访问

```text
/(rce|cmd|shell|backdoor|wso|b374k|c99|cmdjsp|gsl|godzilla|behinder|ants|n1nty)\.(php|jsp|asp|aspx|asa|cer|cdx)(\?|$)
```

问题：

| 类型 | 说明 |
|---|---|
| 误报 | `shell.php`、`cmd.php`、`rce.php` 在正常项目、框架、示例代码中可能存在 |
| 漏报 | 文件名列表很短；随机名、`shell1.php`、`my-shell.php`、`cmd_upload.php` 不命中 |
| 漏报 | 扩展名只覆盖 php/jsp/asp/aspx/asa/cer/cdx；漏 `.phtml`、`.php5`、`.php7`、`.phar`、`.jspx`、`.jspf`、`.ashx`、`.asmx`、`.cfm`、`.cgi`、`.pl`、`.py`、`.rb` |
| 漏报 | 路径参数/路径信息：`/shell.php/abc`、`/shell.php;jsessionid=...`、`/shell.php%00` |
| 漏报 | 编码/大小写/点段变体依赖 `http.uri` 归一化，未验证双重编码 |
| 误报/漏报 | 只按名字判断，无法确认是否是 WebShell |
| 结构 | `any any -> any any`；无 `$EXTERNAL_NET`/`$HOME_NET`；无响应侧 |

### 1.2 9104002 · 脚本文件携带命令类参数

```text
/\.(php|jsp|asp|aspx)\?[a-z0-9_]*=(cmd|exec|command|passwd|pwd|z0|z1|z2|eval)/i
```

这个 PCRE 的实际语义是：

- 匹配 `.php?<param>=` 后，**值**以 `cmd`/`exec`/`command`/... 开头；
- 对典型 WebShell：

```text
/shell.php?cmd=id
/shell.php?exec=whoami
/shell.php?z0=...
```

`=` 后面是 `id`/`whoami`/base64，而不是 `cmd`/`exec`/`z0`，因此**不命中**。
它反而会命中：

```text
/shell.php?x=cmd
```

这是误报，而且没有利用语义。

其他问题：

- 只匹配第一个查询参数，不匹配 `&cmd=`、`&exec=`；
- 不检查 POST Body、Cookie、请求头；
- 参数名 `[a-z0-9_]*` 允许空；没有覆盖 `c`、`pass`、`action`、`method`、`func`、`z3` 等常见管理端参数；
- 扩展名只覆盖 php/jsp/asp/aspx；
- 没有命令值/编码检测；
- 没有响应侧确认；
- `any any -> any any`；
- 没有测试/CI。

### 1.3 两条规则共同的问题

- 没有来源/方向：`any any -> any any`；
- 没有请求体：POST WebShell 命令完全漏报；
- 没有 Cookie：Behinder/Godzilla/AntSword 等常用 Cookie/参数通道漏报；
- 没有响应：无法确认命令输出、文件管理页面、上传/下载行为；
- 没有 `flowbits` 请求+响应关联；
- 没有 Lua 解码/归一化；
- 没有 `tier`，无法区分告警与线索；
- 没有 `$SCANNER_NET`/业务白名单；
- 元数据 `confidence High` 对“文件名命中”明显过强。

## 2. 检出率与误报率

### 2.1 为什么不能给百分比

当前没有：

- 带标签的 WebShell 通信 PCAP/流量集；
- 与本案 SID 对齐的正反例；
- 生产流量 shadow 运行结果；
- WebShell 管理工具（AntSword/Behinder/Godzilla/China Chopper/WSO/b374k/c99）的版本化样本。

因此不能声称“检出率 X% / 误报率 Y%”。

### 2.2 机制判断

| 规则 | 检出能力 | 误报风险 |
|---|---|---|
| 9104001 | 只覆盖少量固定文件名；变体/随机名/其他扩展名漏报 | 高：正常 `shell.php`/`cmd.php` 会命中 |
| 9104002 | 对典型 `?cmd=id`、`?exec=...`、`?z0=...` **基本无效** | 中：`?x=cmd` 等值匹配会误报 |

**综合判断**：原规则对真实 WebShell 通信的覆盖率低，对正常业务文件名的误报高。
它不是“精确规则”，只是“文件名线索”。

## 3. 后门通信盲区

### 3.1 请求通道盲区

- URI 查询参数：`?cmd=`、`?exec=`、`?command=`、`?c=`、`?pass=`、`?pwd=`、
  `?z0/z1/z2`、`?action=`、`?method=`、`?func=`、`?do=`；
- POST Body：`cmd=id`、`pass=...`、`z0=...`、JSON、multipart；
- Cookie：Behinder/Godzilla/AntSword 的会话/密钥参数；
- 请求头：自定义 `X-*`、`User-Agent: antSword/Behinder/Godzilla`；
- Base64/URL 编码参数：`z0`、`pass`、`cmd` 值；
- 路径：随机文件名、无扩展名、`.phtml/.php5/.jspx/.ashx`、路径参数。

### 3.2 响应侧盲区

- 命令输出：`uid=...`、`gid=...`、`root:x:0:0`、`www-data`、
  `Microsoft Windows`、`Volume Serial Number`、`Directory of`；
- 文件管理：`Index of /`、Upload/Download/Delete/Rename/chmod；
- 错误回显：`eval()'d code`、`Fatal error`、`java.lang.Runtime`、`ProcessBuilder`；
- 文件下载/上传响应；
- `Set-Cookie` 认证/会话特征。

### 3.3 工具/协议盲区

- AntSword：`z0/z1/z2`、base64、`pass`；
- Behinder/Godzilla：AES 加密参数，密文随机；
- China Chopper：短参数、`cmd`；
- WSO/b374k/c99：文件管理/命令参数；
- 一句话木马：随机文件名、短 payload；
- 加密/混淆/分块/压缩 payload；
- 访问频率/同一脚本多参数变化（需跨包聚合，规则内不能做全量统计）。

### 3.4 上下文盲区

- 正常业务也可能有 `shell.php`、`cmd.php`；
- 正常 API 也可能有 `cmd` 参数（如命令模式/配置）；
- 授权渗透/红队工具；
- 反向代理/CDN/NAT 改变来源方向；
- HTTPS 未解密、HTTP/2/HTTP/3。

## 4. 可通过 Lua 加强的能力

### 4.1 请求侧：`webshell_request.lua`

检查 URI、查询参数、Body、Cookie、请求头，解析参数名和值：

- 已知 WebShell 文件名（但作为**线索**，不单独升级 Critical）；
- 常见管理端参数名：
  `cmd, exec, command, execute, shell, pass, password, pwd, z0, z1, z2, z3,
   action, method, func, function, do, run, eval, code, upload, download`；
- 参数值中的命令/路径/代码语义：
  `id, whoami, cat /etc/passwd, ls, dir, ipconfig, net user, uname,
   system(, exec(, eval(, assert(, passthru(, shell_exec(`；
- Base64 解码：
  - 用 `suricata.base64` 解码 `z0/pass/cmd` 值；
  - 解码后再次检查命令/代码标记；
  - **不能解密** Behinder/Godzilla 的 AES 密文。
- 工具指纹：
  - `User-Agent`/Header 中的 `antSword`、`Behinder`、`Godzilla` 等；
  - 仅作为辅助信号，可伪造。

### 4.2 响应侧：`webshell_response.lua`

请求规则设置 `flowbits:set,webshell_probe`，响应规则：

- `flowbits:isset,webshell_probe`；
- `http.response_body`/Lua `response_body()`；
- 检查命令输出、文件管理、错误回显；
- `by_dst` 限频；
- `tier alert` 仅在命令输出/文件管理明确时，否则 `tier triage`。

### 4.3 规则建议

| 建议 SID | 内容 | tier |
|---|---|---|
| 9104001 | 已知 WebShell 文件名访问（保留，降为 triage；或叠加参数/响应） | triage |
| 9104002 | 修复：URI/Body/Cookie 中的命令参数名 + 值语义 | alert/triage |
| 9104003 | Base64/编码 WebShell 参数（AntSword/China Chopper 类） | alert |
| 9104004 | 响应侧命令输出/文件管理确认（flowbits） | alert |
| 9104005 | WebShell 管理工具 UA/Header 指纹 | telemetry |

### 4.4 修复 9104002 的关键

正确方向是匹配**参数名**，不是值：

```text
[?&](cmd|exec|command|execute|pass|password|pwd|z0|z1|z2|z3|action|method|func|do|run)=
```

并且要覆盖：

- `?cmd=id`；
- `&cmd=id`；
- POST Body `cmd=id`；
- Cookie `pass=...`；
- 参数名大小写/URL 编码；
- 参数值中的命令/代码语义。

## 5. 误报控制

- 已知文件名只做 `tier triage`，不直接 Critical；
- 参数名 + 命令值/代码语义组合，避免 `?cmd=config` 之类正常参数；
- 响应侧确认只在命令输出/文件管理标记出现时升级；
- 授权扫描器/红队/业务 `shell.php` 用 `$SCANNER_NET`/suppress；
- 不把“文件名存在”当作“后门通信成功”；
- 对加密工具（Behinder/Godzilla）只做行为/响应线索，不做“已确认”。

## 6. 验证用例

原先没有 CI；现已新增 `suricata-backdoor-c2.yml`，当前覆盖 17 个 PCAP。
后续可继续补充：

- 正例：
  - `shell.php?cmd=id`
  - `cmd.php?exec=whoami`
  - POST `cmd=id`

- `suricata -T` 加载规则/Lua；
- 上传 `eve.json`/日志作为 artifact。

| SID | 内容 | Lua |
|---|---|---|
| 9104001 | 已知 WebShell 文件名访问（triage，flowbits） | `webshell_path.lua` |
| 9104002 | URI/Body/Cookie/Header 命令参数与值语义 | `webshell_param.lua` |
| 9104003 | 响应侧命令输出/文件管理/错误回显 | `webshell_response.lua` |
| 9104004 | 管理工具 UA（telemetry） | 规则内 pcre |

- 方向：`$EXTERNAL_NET -> $HOME_NET`，响应 `$HOME_NET -> $EXTERNAL_NET`；
- 9104002 已修复原规则“参数名/值写反”的问题；
- 支持 base64 参数解码（纯 Lua，避免沙箱 base64 异常）；
- 响应侧使用 `flowbits` 关联；
- 不使用 `any any`、不使用 `detection_filter`；
- CI：run `42384924560`，17/17 用例通过。

## 8. 结论

原规则的问题不是“规则数量少”，而是：

1. 9104001 是**文件名黑名单**，误报高、变体漏报；
2. 9104002 的 PCRE **参数名/值写反**，对典型 `?cmd=id` 无效；
3. 只看 URI，RequestBody/Cookie/Header 全漏；
4. 没有响应确认，无法判断命令执行；
5. 没有测试/CI。

优先用 Lua 做：

1. 请求侧参数名 + 值语义；
2. Base64 解码（可解 AntSword/China Chopper，不可解 Behinder/Godzilla AES）；
3. 响应侧命令输出/文件管理确认；
4. 已知文件名降为 triage。

当前规则/Lua 已落地并通过 CI（run `42384924560`，17/17）；
仍然不能声称生产“零误报”，也不能给出未经标注语料验证的检出率/误报率。
