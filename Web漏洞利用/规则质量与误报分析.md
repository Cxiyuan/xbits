# Web 漏洞利用规则 · 质量、检出率、误报率与盲区分析

## 0. 结论摘要

原 `03-Web漏洞利用.rules` 的核心问题不是“规则少”，而是：

1. **23 条规则全部只看 `http.uri`**，完全看不到 POST 请求体、Cookie、请求头；
2. **全部使用 `any any -> any any`**，没有来源/方向约束；
3. **多条规则把普通单词当成攻击**（`information_schema`、`fastjson`、`ognl`、`thinkphp`、`.action`），误报高、检出低；
4. **Shiro 规则把 `rememberMe` 写在 URI 上**，而它实际是 Cookie 头，基本无效；
5. **Log4Shell 只查 URI**，而真实利用大量出现在 `User-Agent`、`X-Api-Version`、`Referer`、Cookie 和 Body；
6. **没有正/反例 PCAP、没有 `suricata -T`、没有 CI**，无法量化检出率或误报率。

重构后保留核心 SID，合并低质量规则，使用 Lua 同时检查 URI、请求体、Cookie、请求头，
并新增 SSRF、XXE、SSTI、WebShell 上传能力。当前 GitHub Actions 结果：
**9 条规则加载成功，34/34 PCAP 用例通过**（run `42377078821`，commit `b933f57`）。

## 1. 原规则质量问题逐项审计

### 1.1 结构性问题（23 条全部存在）

| 问题 | 影响 |
|---|---|
| `alert http any any -> any any` | 无来源/方向约束；无法区分外部攻击、内部扫描、正常业务 |
| 只检查 `http.uri`/`http.uri.raw` | POST body、JSON、Cookie、请求头中的载荷全部漏报 |
| 没有 `content` + `fast_pattern` 的统一快筛策略 | 短词 content 可能被 MPM 选中，性能与语义不稳定 |
| 没有请求体读取 | SQLi/Log4Shell/命令注入/反序列化主要在 Body |
| 没有 URL 解码/双重编码/空白归一化 | `%27`、`%252e`、`/* */`、`+` 等变体漏报 |
| 没有响应侧确认 | 无法区分“尝试”和“成功”，也无法提供利用结果线索 |
| 没有测试/CI | 规则是否加载、是否命中、是否误报都未验证 |

### 1.3 为什么不能给出可信的“检出率/误报率”

当前仓库没有带标签的生产流量或公开的 Web 攻击语料与本案 SID 对齐：

- 没有按“规则命中 + 人工确认”标注的数据集；
- 没有按资产/业务白名单标注的负例；
- 没有对同一流量做 shadow 运行。

因此不能声称“检出率 X% / 误报率 Y%”。能给出的是：

- **回归覆盖率**：34 个确定性 PCAP 用例，9 个类别，正例/反例均断言 SID；
- **机制层面的漏报/误报分析**（本文件）；
- **定性判断**：原 Shiro/Struts/Fastjson/OGNL/ThinkPHP 规则属于“高误报、低检出”；原 SQLi/Log4Shell/CMD 属于“URI 单点、Body/Header 漏报”。

生产检出率/误报率必须在影子期用真实流量、资产标签和人工确认来测量，不能从规则数量推断。

## 2. 原规则的主要盲区

### 2.1 请求位置盲区

| 位置 | 原规则 | 风险 |
|---|---|---|
| POST body / JSON | 完全不看 | SQLi、Log4Shell、命令注入、Fastjson、OGNL、XXE、SSTI 大量漏报 |
| Cookie | 完全不看 | Shiro rememberMe、SQLi、命令注入漏报 |
| 请求头 | 完全不看 | Log4Shell 的 UA/Referer/X-Api-Version 漏报 |
| multipart | 完全不看 | WebShell 上传漏报 |
| query + path | 只看原始 URI | 编码/双重编码/点段/反斜杠漏报 |

### 2.2 解析与规范化盲区

- 只做少量字面/PCRE 匹配；
- 没有 URL 解码、双重解码、`+` 转空格；
- 没有 SQL 注释 `/**/`、`--`、换行/制表符归一化；
- 没有反斜杠、点段、大小写、Unicode/overlong 处理；
- 没有 JSON key/value 语义，只是字符串搜索；
- 没有 multipart 字段解析。

### 2.3 语义盲区

- `information_schema` 单独出现不是注入；
- `fastjson`/`ognl`/`thinkphp` 出现在 URI 里不是利用；
- `.action`/`.do` 是正常 Java 端点；
- `rememberMe` 在 URI 里不是 Shiro Cookie；
- Log4Shell 的真实入口经常是 Header，而不是 URI；
- 命令注入不要求命令后跟空格，`;id`、`|id` 很常见；
- 单个 `../` 也可能完成穿越，原规则要求 3 个是明显漏报。

### 2.4 检测链路盲区

- 没有响应侧确认（200/500/回显/命令输出）；
- 没有与工具指纹、资产、认证状态联动；
- 没有授权扫描器/业务白名单；
- 没有 HTTPS 解密、HTTP/2/HTTP/3 覆盖；
- 没有跨包聚合（规则内也不应做全局计数）。

## 3. 重构后的规则设计

### 3.1 规则数量与 SID

保留核心 SID，合并低质量规则：

| 新规则 SID | 类别 | Lua |
|---|---|---|
| 9103001 | SQLi（UNION/报错/时间/布尔/元数据） | `web_sqli.lua` |
| 9103008 | 路径穿越 / LFI | `web_traversal.lua` |
| 9103013 | Log4Shell / JNDI | `web_log4shell.lua` |
| 9103015 | 命令注入 | `web_cmdi.lua` |
| 9103018 | Java 反序列化/框架利用 | `web_deser.lua` |
| 9103101 | SSRF | `web_ssrf.lua` |
| 9103102 | XXE | `web_xxe.lua` |
| 9103103 | SSTI | `web_ssti.lua` |
| 9103104 | WebShell 上传 | `web_upload.lua` |

合并/删除的原 SID：

- 9103002-9103007 → 9103001；
- 9103009-9103012 → 9103008；
- 9103014 → 9103013；
- 9103016-9103017 → 9103015；
- 9103019-9103023 → 9103018；
- 9103018 原 Shiro URI 规则无服务端可观测性；不把仅 `rememberMe` Cookie 长度作为告警。

### 3.2 请求范围与方向

```text
$EXTERNAL_NET -> $HOME_NET   外部入站 Web 攻击
```

不再使用 `any any -> any any`。内部横向/出站 Web 攻击可在后续场景单独加规则。

### 3.3 检测源

Lua 同时读取：

- `request_uri_raw()` / `request_uri_normalized()`；
- `request_body()`（最多 16 KiB）；
- `request_headers_raw()`；
- `request_header("Cookie")`；
- `Content-Type`（上传/XML/JSON 辅助）。

### 3.4 各 Lua 的检测语义

- **SQLi**：UNION+SELECT、报错函数、时间函数、MSSQL、布尔恒真、`information_schema` + SQL 上下文；
- **Traversal/LFI**：单级/多级 `../`、编码/反斜杠/双重编码、敏感文件、协议包装器、文件参数；
- **Log4Shell**：URI/Header/Body/Cookie，`jndi:` + 协议，解 `${lower:...}`、`${upper:...}`、`${::-...}` 嵌套；
- **CMDi**：Shell 元字符后紧跟系统命令，支持 `;id`、`|id`、`$(id)`、`${IFS}`、换行/编码；普通 `&id=2` 不算；
- **Deser**：Fastjson `@type` + 危险类、OGNL Runtime/ProcessBuilder、ThinkPHP `invokefunction` 调用链、Java `rO0AB/aced0005`、PHP 序列化标记；
- **SSRF**：URL/跳转/代理/抓取参数 + 内网/云元数据/危险协议；
- **XXE**：`<!ENTITY` + `SYSTEM/PUBLIC`；
- **SSTI**：模板定界符 + 算术/危险对象访问；
- **Upload**：脚本扩展名 + 代码标记（`<?php`、`<%`、`eval(`、`system(` 等）。

### 3.5 分级

- `tier alert`：SQLi、Traversal/LFI、Log4Shell、CMDi、Deser、XXE；
- `tier triage`：SSRF、SSTI、Upload（业务白名单误报更高）。

## 4. 误报控制

已做的控制：

1. 不再用单个单词 `information_schema/fastjson/ognl/thinkphp/.action` 告警；
2. SQLi 需要语法上下文；`information_schema` 必须叠加 `select/from/union/where` 等；
3. Traversal 单级 `../` 必须叠加敏感文件；两级以上才独立成立；
4. CMDi 要求元字符 + 命令，`&id=2`、`&cat=3` 不算；
5. Fastjson 需要 `@type/autoType` + 危险类；
6. OGNL 需要 `%{` + `@java.`/`#_memberAccess`/`ognl.`；
7. ThinkPHP 需要 `invokefunction` + 调用链；
8. XXE 需要 `<!ENTITY` + `SYSTEM/PUBLIC`；
9. SSTI 需要模板定界符 + 算术/危险对象；
10. Upload 需要脚本扩展名 + 代码标记。

仍需外部抑制：

- 授权扫描器/WAF 自检流量；
- 业务本身使用模板表达式、文件下载、URL 抓取、XML、上传源代码；
- 建议按 `tier` + 资产标签 + `$SCANNER_NET` 抑制。

## 5. 盲区与未覆盖项

以下明确不在当前验证范围：

1. **HTTPS 未解密**：看不到 URI/Body/Header。
2. **HTTP/2/HTTP/3**：`suricata.http` Lua API 以 HTTP/1 事务为主；HTTP/3/QUIC 加密流量不可见。
3. **响应侧成功确认**：未判断命令输出、SQL 报错、文件内容回显。
4. **请求体超过 16 KiB**：Lua 只读取前 16 KiB，超长 payload 可能漏报。
5. **压缩/分块/编码体**：未做 gzip 解压、复杂 chunked 重组、base64 解码嵌套。
6. **JSON/multipart 语义解析**：目前是字符串搜索，不是结构化解析。
7. **SQL 注释变体**：`/*!50000union*/`、Unicode/overlong、参数污染等未完整覆盖。
8. **Shiro rememberMe**：加密 payload 与正常会话无法仅靠长度区分，未单独告警。
9. **盲 SSRF/反连**：没有 OOB/DNS 回调关联。
10. **二阶注入/存储型**：当前只看单请求，不看后续请求/数据库回显。
11. **业务白名单**：未内置资产/API 允许列表；SSRF/SSTI/Upload 需 triage。
12. **性能**：9 条 Lua 规则会在每个 HTTP 请求上执行并可能读取 16 KiB Body；
    尚未做吞吐量压测，生产需 shadow 评估；后续可用候选词预过滤/dispatcher 优化。

## 7. 剩余问题的可解决性评估

| 问题 | 结论 | 可落地方案 | 不能解决的部分 |
|---|---|---|---|
| Body 只读前 16 KiB | **可缓解/基本解决** | 用 `http.request_body` 原生 buffer + `content/pcre` 覆盖长 Body；Lua 改为逐 chunk 扫描并保留重叠窗口；提高 `security.lua.max-bytes` 需评估内存 | 不能无限读取；Lua 有内存/指令预算，超大 Body 必须设置上限或走原生 buffer |
| 无响应侧成功确认 | **可部分解决** | 增加 `response_body` 规则：SQL 报错、命令输出、文件内容/云密钥标记；请求规则用 `flowbits` 标记尝试，响应规则确认 | 不是确定性利用验证；错误页/本地化/WAF/盲注会误报或漏报；响应体可能压缩/超长 |
| JSON/multipart 字符串搜索 | **multipart 可较好解决；JSON 只能部分解决** | multipart 用 `file.data`/`file.name`/`fileext` 原生缓冲区；JSON 写最小 key/value 扫描器，只提取 `@type`/`autoType` 等关键字段 | Suricata 8.0.8 没有 JSON body 解析关键字；Lua 沙箱没有 JSON 库；完整 JSON（嵌套、\u 转义、重复键）需外部解析器，不在规则内 |
| Shiro rememberMe 无法区分 | **不能可靠解决** | 只能检测未加密 Java 序列化 magic、`deleteMe`、异常 Cookie 等弱信号；`suricata.base64` 可解码，但没有 AES 解密 | 常见 Shiro 使用 AES 加密 payload；无密钥时密文与正常会话不可区分；长度/熵启发式误报高，不应强告警 |
| SSRF/SSTI/Upload 白名单误报 | **可降低，不能消除** | 用 `$SCANNER_NET`/资产组/`threshold.config` suppress；Upload 用 `fileext`/目标端点 allowlist；SSTI 只保留危险对象访问；SSRF 用目标地址/业务 URL allowlist | Lua 沙箱不能读取本地 allowlist 文件，dataset 也不直接暴露给 Lua；没有资产/业务上下文时无法通用判断“合法内部 URL/模板/上传” |

### 7.1 推荐顺序

1. **multipart 改用 `file.data`/`file.name`/`fileext`**：收益直接、无需手写解析器；
2. **响应侧确认规则**：先做 SQL 报错、命令输出、文件内容三类高价值标记；
3. **Body 原生 buffer/分块扫描**：把 16 KiB 固定上限改为可配置并覆盖长 Body；
4. **最小 JSON key 扫描器**：只解析 `@type`/`autoType`/危险类，不做完整 JSON；
5. **Shiro 不加强告警**：最多做 `tier telemetry`；生产需要应用侧解密/日志；
6. **白名单/抑制**：按资产和授权网络实施，不在规则中硬编码公共后缀或云厂商。

### 7.2 对“能否解决”的直接回答

- **能解决/基本解决**：Body 固定 16 KiB、multipart 结构化、响应侧部分成功信号；
- **只能部分解决**：JSON 结构化、响应侧确定性确认、SSRF/SSTI/Upload 误报；
- **不能可靠解决**：Shiro 加密 rememberMe 与正常会话的区分（无密钥/解密时）。
