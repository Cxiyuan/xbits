# 侦察与攻击工具指纹 · 误报分析与规则缺陷

## 1. 结论

原 `01-侦察与攻击工具指纹.rules` 的核心问题是：**把 29 条“UA 子串匹配”当成高置信攻击结论**。
UA 可以被一行命令改掉，且大量正常 API/健康检查/CI 客户端会使用同样的 UA。
因此原规则既存在漏报（改 UA 即绕过、HTTPS 完全看不到），也存在明显误报（`Java/`、`okhttp`、
`curl`、`python-requests`、`httpx` 子串等）。

本文件把问题拆成三层：

1. **规则是否真实有效**：哪些 SID 的匹配条件过宽、过窄或根本没有服务端指纹；
2. **检测层是否可运营**：方向、分级、限频、抑制、ATT&CK 标注是否一致；
3. **能力边界是否被夸大**：UA 规则对 HTTPS、随机 UA、自定义 UA 的覆盖为零。

优化后的规则见同目录 `侦察与攻击工具指纹规则.rules`，Lua 见 `lua/`。
所有结论按以下状态标注：

- **已验证**：有 Suricata 8.0.8 文档/源码依据，或 GitHub Actions 结果；
- **待验证**：需要 CI/PCAP 断言；
- **未验证**：仅设计假设，不能作为上线依据。

当前规则与测试的 CI 结果：**已验证**。GitHub Actions
[run 42374685682](https://github.com/Cxiyuan/ips/actions/runs/42374685682)
在 commit `288deac` 上通过，26/26 个 PCAP 用例全部通过。
仍然不承诺生产环境“零误报”；只声明给定回归集无已知误报。

## 2. 对已提出问题的逐条核对

### 2.1 “只靠 UA，容易规避” —— 成立

原 27 条工具规则全部是 `http.user_agent; content:"..."`。
攻击者用 `--user-agent`、`-H "User-Agent: ..."`、随机 UA 即完全绕过。
UA 只能作为**工具指纹线索**，不能作为“存在自动化攻击行为、置信度最高”的证据。

### 2.2 “python-requests/curl/Java/okhttp/aiohttp 会误报” —— 成立

原 9101029 把以下客户端统一当成“高频脚本化攻击”：

```text
curl/ Wget/ python-requests/ Python-urllib/ Go-http-client/
Java/ okhttp aiohttp libwww-perl LWP::Simple
```

这些 UA 在 API 网关、服务间调用、CI、健康检查、移动端/Android 后端中非常常见。
尤其 `Java/` 会命中任何 Java HTTP 客户端，`okhttp` 会命中大量正常 Android/服务端调用。
原规则虽然有 `detection_filter count 60/60`，但达到阈值后**每条请求都告警**，会形成告警风暴。

### 2.3 “Shodan/Censys/Expanse/l9explore 不应和攻击工具同级” —— 成立

这些是互联网测绘/资产发现爬虫，可能是第三方研究、攻击前侦察，也可能是企业自身资产暴露面扫描。
把它们标成 `attempted-recon`（classification priority 2）并给 `confidence High`，会误导 SIEM 优先级。
优化后：

- 单独 `classtype:network-scan`；
- `severity Info` / `tier telemetry`；
- 只保留“被扫描”线索，不直接升级为攻击告警。

### 2.4 “threshold 已弃用” —— **不成立（Suricata 8.0.8）**

Suricata 8.0.8 的用户手册仍然完整记录 `threshold` 与 `detection_filter`
（`doc/userguide/rules/thresholding.rst`），源码中也仍有 `detect-threshold.c`。
8.0.8 没有弃用 `threshold`，也没有要求改用 `event_filter` 作为规则内替代。

但原规则对语义的使用确实有问题：

- `threshold: type limit, count 1, seconds 60`：每个源每规则每分钟只告警一次，适合去重，
  但会隐藏“同一工具持续扫描不同路径”的规模信息；
- `detection_filter`：达到初始阈值后**每次匹配都执行动作**，不适合做告警抑制；
- `threshold: type both`：达到 count 后每 `seconds` 只告警一次，适合“高频行为”规则。

优化后不再使用 `detection_filter`；工具指纹用 `type limit` 去重，行为频率用 `type both`。
`event_filter` 属于全局阈值配置，不是规则关键字；需要全局抑制时应放在 `threshold.config`。

### 2.5 “detection_filter 会告警泛滥” —— 成立

原 9101028：`content:!"Mozilla"; detection_filter 100/60`，
第 101 条非 Mozilla 请求开始**每条都告警**；在 NAT/CI/API 网关上可以瞬间打满。
原 9101029：`detection_filter 60/60`，第 61 条开始每条都告警。
优化后 9101028/9101029 改为 `threshold: type both, count 50/60 或 60/60`，每个源每个周期最多一条。

### 2.6 “httpx / Nuclei 子串过宽” —— 成立

- `content:"httpx"` 会命中 `python-httpx/0.27.0`（正常 Python 库）；
- `content:"Nuclei"` 会命中任何包含 `Nuclei` 的 UA 子串；
- `content:"Nmap Scripting Engine"` 在 NSE UA 被包在 `Mozilla/5.0 (compatible; ...)` 时，
  如果只用 `^Nmap` 会漏报，所以需要允许分隔符边界而不是简单 `startswith`。

优化后每条规则同时保留：

- `content` 作为 MPM 快筛；
- `pcre` 做 `^` 锚定或 `[\s;(]` 边界校验；
- `httpx` 使用 `^httpx(?:\/|$)`，明确排除 `python-httpx/`。

### 2.7 “方向不一致” —— 成立

原规则：

- 27 条 `any any -> any any`；
- 9101028 `any any -> any any`；
- 9101029 `$HOME_NET -> $EXTERNAL_NET`。

结果是：

- 外部扫描内部（最常见）没有方向约束；
- 内网外联（失陷主机扫描外部）只覆盖脚本客户端，不覆盖工具 UA；
- 内网横向完全没有覆盖；
- 如果 `$EXTERNAL_NET` 未显式配置，9101029 可能永远不命中。

优化后按方向拆分：

| 方向 | 用途 | 规则 |
|---|---|---|
| `$EXTERNAL_NET -> $HOME_NET` | 外部对内部服务侦察 | 9101001-9101029、9101101、9101103 |
| `$HOME_NET -> $EXTERNAL_NET` | 内部服务响应 | 9101102、9101104、9101107 |
| `$CLIENT_NET -> $EXTERNAL_NET` | 内网主机外联/外发扫描 | 9101029、9101105 |
| `$HOME_NET -> $HOME_NET` | 内网横向 | 9101106 |

### 2.8 “ATT&CK 粒度粗” —— 成立

原规则全部写 `T1595.002`。实际应区分：

| 工具类别 | 更合适的技术 |
|---|---|
| ffuf/gobuster/feroxbuster/DirBuster | `T1595.003` Wordlist Scanning |
| Nuclei/Nikto/WPScan/Nessus/OpenVAS/Acunetix | `T1595.002` Vulnerability Scanning |
| sqlmap/commix/XSStrike | `T1190` Exploit Public-Facing Application（利用尝试） |
| Shodan/Censys/Expanse/l9explore/zgrab/masscan | `T1595.001` Scanning IP Blocks |

优化规则已按类别更新 `attack_technique`，并在 `metadata` 中保留 `tool`、`tier`。

## 3. 原规则中未被指出的其他问题

### 3.1 HTTPS/TLS 盲区（最严重的漏报）

所有规则都是 `alert http`。外部扫描器现在绝大多数走 `https://`；
Suricata 不解密 TLS 时**看不到 User-Agent**，这些 SID 对 HTTPS 扫描的检出率接近 0。
本规则集没有、也不能仅靠 UA 解决这个问题。需要：

- 在合规前提下配置 TLS 解密；或
- 用 `tls.sni`、JA3/JA4、连接频率、证书/ALPN 等旁路信号做补充；或
- 接受“本场景只覆盖明文 HTTP”的能力边界。

文档和 `msg` 不能暗示“已覆盖 HTTPS 扫描”。

### 3.2 `content:!"Mozilla"` 的缺失/空 UA 语义

9101028 只有一条否定 content，没有正向 content。
Suricata 8.0.8 的内容检查在 `buffer == NULL` 时直接返回 0（源码
`detect-engine-content-inspection.c`），因此**缺失 UA 大概率不会命中**；
但空值 UA（`User-Agent:` 后为空）是长度为 0 的非 NULL 缓冲区，否定 content 可能命中。
该行为需要 PCAP 断言确认（当前标注：**待验证**）。
无论哪种结果，用“非 Mozilla”作为唯一条件都不可运营，优化后已删除该写法。

### 3.3 `threshold type limit` 掩盖规模

27 条工具规则每条 `count 1/60`。同一攻击者用 ffuf 扫描 10 万个路径，
每个 SID 每分钟只出一条；SOC 看不到请求量、路径分布和响应码分布。
去重应该由 SIEM/聚合层完成，规则层至少保留 `type both` 的频率线索，或输出 `flowbits`/计数给关联规则。

### 3.4 没有路径、方法、响应码、请求体上下文

原规则没有：

- `http.uri` / `http.method` / `http.request_body`；
- `http.stat_code` / `http.response_line`；
- 敏感路径（`/.git/`、`/.env`、`/actuator/env`、`/server-status`、`/wp-login.php` 等）；
- 请求与响应联合确认。

因此无法区分“扫描器请求了首页”和“扫描器读到了 `/.git/config`”。
优化后新增：

- 请求侧：已知工具 + 敏感路径（Lua）；
- 响应侧：`flowbits` + `http.stat_code` 200/401/403 联合确认；
- 不依赖 UA 的外部源敏感路径高频探测（请求/响应两侧 `threshold: type both`）。

### 3.5 没有资产/来源白名单

原规则没有 `$SCANNER_NET`、授权扫描器、API 网关、健康检查的抑制策略。
Nessus/OpenVAS/Acunetix 很可能是企业自己授权的漏扫；直接告警会产生大量“已知正常”。
优化后：

- 规则方向区分外部/内网；
- Lua 对健康检查 UA 做明确排除（`kube-probe`、`ELB-HealthChecker`、`GoogleHC` 等）；
- 文档要求用 `$SCANNER_NET`/全局 suppress 处理授权扫描器；
- 不把公共后缀或整个云厂商写成白名单。

### 3.6 无效或低价值规则

- **9101017 Wappalyzer**：Wappalyzer 是浏览器扩展/前端技术识别，请求由浏览器发出，
  不会在服务端请求里带 `Wappalyzer` UA。该规则基本没有服务端可观测性，已删除。
- **9101011 masscan**：masscan 主要是 SYN 扫描；只有 `--banners` 的 HTTP banner 抓取才会带
  `masscan/` UA。保留但降为 `tier telemetry`，并改为精确 `^masscan/[0-9]`。
- **9101014 zgrab**：互联网测绘，降为 `network-scan`/telemetry。
- **9101024-9101027**：Shodan/Censys/Expanse/l9explore，降为测绘线索，不再与攻击工具同级。

### 3.7 元数据与语义不一致

- 文件头写“命中即代表存在自动化攻击行为，置信度最高” —— 过度承诺；
- 9101024-9101027 是 `severity Info` 却使用 `classtype:attempted-recon`（priority 2）；
- 9101028/9101029 是 `confidence Low` 却和 High 规则同队列；
- 缺少 `tier`，SIEM 无法按告警/线索/遥测分流。

优化后统一：

- `tier alert`：精确工具指纹或工具+敏感路径+响应确认；
- `tier triage`：需要人工/资产上下文确认；
- `tier telemetry`：测绘、通用脚本客户端、低频 banner；
- `classtype` 与 `severity` 尽量一致（Info/telemetry 用 `network-scan`）。

### 3.8 缺少 HTTP 头部/顺序/方法等辅助信号

原规则只有 UA。绕过 UA 后没有第二信号。优化后加入：

- 请求路径（敏感路径）；
- 响应码（2xx/3xx/4xx/5xx）与响应体泄露标记；
- 频率（`threshold: type both`）；
- 方向（外部/外联/横向）；
- Lua 规范化（大小写、百分号编码、绝对 URI、重复斜杠）。

仍未加入的（避免过度设计/高误报）：

- `http.header_names` 头部顺序：不同版本工具差异大，维护成本高；
- 请求体 payload：需要按工具/漏洞类型建模，误报和性能风险更高；
- JA3/JA4：Go/Java/Python 工具与正常客户端重叠大，单独使用误报高。

### 3.9 没有测试与 CI

原文件没有正例/反例 PCAP，也没有 `suricata -T` 加载验证。
本仓库已新增：

- `test/generate_recon_pcaps.py`：合成 HTTP 正反例；
- `test/recon_cases.json`：按 `signature_id` 断言；
- `test/suricata-recon-ci.yaml.in`：场景专用配置；
- `.github/workflows/suricata-recon-tools.yml`：精确 8.0.8 构建 + 回归。

CI 未跑通前，本文件所有“已优化”结论都只能算设计完成，不能算验证完成。

## 4. 优化后的检测设计

### 4.1 精确 UA 指纹（tier alert/telemetry）

每条工具规则使用：

```text
http.user_agent; content:"<tool token>"; nocase; fast_pattern;
pcre:"<^锚定或分隔符边界>";
```

关键修正：

| 工具 | 原匹配 | 优化后 | 目的 |
|---|---|---|---|
| httpx | `content:"httpx"` | `^httpx(?:\/|$)` | 排除 `python-httpx/` |
| Nuclei | `content:"Nuclei"` | `^Nuclei(?:\b|[\/ -])` | 排除任意子串 |
| Nmap NSE | `content:"Nmap Scripting Engine"` | `(?:^|[\s;(])Nmap Scripting Engine\b` | 兼容 Mozilla 包裹 |
| gobuster | `content:"gobuster/"` | `^gobuster/[0-9]` | 排除普通文本 |
| sqlmap | `content:"sqlmap/"` | `^sqlmap/[0-9]` | 排除普通文本 |
| Shodan | `content:"Shodan"` | `(?:^|[\s;(])Shodan\/` | 兼容 compatible 包裹 |

### 4.2 工具 + 敏感路径 + 响应确认

```text
请求: 已知工具 UA + 敏感路径 -> flowbits:set,recon_sensitive_probe
响应: flowbits:isset + HTTP 2xx -> 9101102（软 404 抑制后的成功访问）
响应: flowbits:isset + HTTP 401/403 -> 9101107（被保护但仍在探测）
```

Lua `recon_context.lua` 负责：

- UA 精确边界；
- URI 小写、百分号解码、去除绝对 URI 前缀、合并重复斜杠；
- `/.git/`、`/.env`、`/wp-config.php`、`/actuator/`、`/server-status` 等高价值路径。

### 4.3 不依赖 UA 的敏感路径高频探测

```text
外部源 + 敏感路径 + 20 次/60 秒 -> 9101103（tier triage）
响应 2xx/3xx/4xx/5xx -> 9101104（tier triage）
```

这弥补“攻击者改 UA/随机 UA”的漏报；用 `type both` 限频，避免 404 扫描刷屏。

### 4.4 方向补齐

- 9101105：`$CLIENT_NET -> $EXTERNAL_NET`，内网主机外联使用工具 UA；
- 9101106：`$HOME_NET -> $HOME_NET`，内网横向使用工具 UA；
- 9101029：内网高频脚本客户端外联，telemetry。

### 4.5 不再做什么

- 不再使用 `any any -> any any`；
- 不再使用 `content:!"Mozilla"` 作为唯一条件；
- 不再使用 `detection_filter` 做告警；
- 不再把 Wappalyzer 当作服务端 UA 指纹；
- 不再宣称“UA 命中 = 攻击成功”；
- 不再宣称“覆盖 HTTPS 扫描”。

## 5. 残余风险与能力边界

1. **UA 可伪造**：精确 UA 规则只对“默认配置/未改 UA”的工具有效。
2. **HTTPS 不可见**：未解密 TLS 时，UA 规则对 443 扫描无效；需要解密或旁路信号。
3. **随机/自定义 UA**：依赖 9101103/9101104 的路径+频率行为，仍需资产上下文。
4. **授权扫描器**：Nessus/OpenVAS/Acunetix 可能是正常业务；必须用 `$SCANNER_NET`/suppress 管理。
5. **NAT/代理**：`by_src` 限频在 NAT 后可能把多个客户端合并；需要结合 `http.host`/资产维度。
6. **HTTP/2/HTTP/3**：`suricata.http` Lua API 主要面向 HTTP/1 事务（`ALPROTO_HTTP1`），
   Lua 规则不自动覆盖 HTTP/2；`alert http` 也不解析加密 QUIC 中的 HTTP/3 请求。
7. **“零误报”不可承诺**：本规则集只能做到“在给定回归集上无已知误报”，不宣称生产零误报。
